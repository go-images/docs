# 性能 — `go-images/images` と scikit-image / SciPy の比較 {#performance-go-imagesimages-vs-scikit-image-scipy}

> **基準:** 同じマシンで、現実的な画像サイズを用い、意味が一致する演算について、公平で正直な計測を行います。勝っている結果も負けている結果も示します。「on n'a pas le droit de se tromper」。見せかけの勝利は、本物の敗北よりも悪いからです。

## 方法 {#method}

- **ハードウェア:** Tart の `debian` VM（`aarch64`（arm64）Linux、カーネル 6.12、4 vCPU）1 台です。両方のスタックを、同じ VM 上で続けて実行します。
- **画像:** 決定論的な `512×512`（および `1024×1024`）の RGB(A) 画像です（xorshift / NumPy の乱数生成器）。
- **go-images:** Go 1.26.4、`GOWORK=off`、`go test -bench` を使い、時間は ns/op（計測した反復のうち最良の値）です。色の演算は RGBA で実行し、比較対象は、一致する演算を 3 つの色チャンネルそれぞれに対して実行します。
- **scikit-image / SciPy:** Debian のシステムパッケージ（`python3-skimage` 0.25、`python3-scipy` 1.15、`python3-numpy` 2.2）を使い、`time.perf_counter` で、ウォームアップ後の 20 回のうち最良の値を採ります。ここでの NumPy は、SIMD を使うシングルスレッドの C です。
- **意味の一致**（比較を公平にしている部分です）:
  - ボックスブラー 半径 5 ⇔ チャンネルごとの `scipy.ndimage.uniform_filter(size=11, mode="nearest")`。
  - ガウスぼかし σ=3 ⇔ チャンネルごとの `scipy.ndimage.gaussian_filter(sigma=3, truncate=3,
    mode="nearest")`（こちらの半径が `ceil(3σ)` であるため、truncate は 3 です）。
  - Sobel ⇔ 輝度プレーンに対する `skimage.filters.sobel`（勾配の大きさ）。
  - Erode/Dilate 半径 2 ⇔ チャンネルごとの `scipy.ndimage.grey_erosion` /
    `grey_dilation(size=(5,5), mode="nearest")`。

負荷の高い分離可能なカーネルは、現在 **SIMD の内側ループとマルチコアのタイリング**で動作します。

- **積和（axpy）SIMD カーネル**、つまり連続した float64 プレーンに対する `dst[i] += a*src[i]` が、ガウスの分離可能な畳み込みを担います。チャンネルを連続したプレーンへデインターリーブしているため、カーネルの各タップは 1 回の平坦な axpy になります。2 つのパスの間のバイト丸め済みの中間結果は変わらないので、数値出力は従来のスカラコードと同一です。
- **要素ごとの最小/最大 SIMD カーネル**、つまり `dst[i] = min/max(dst[i], src[i])` が、同様に連続したプレーン上で、分離可能なグレースケールモルフォロジーを担います。
- **マルチコアのタイリング**は、ピクセル数のしきい値を超えると、独立した行（水平パス）と列（垂直パス）を `GOMAXPROCS` 個のゴルーチンに振り分けます。しきい値未満ではシリアルのパスが動きます。結果はワーカー数に依存しません。

アーキテクチャごとの SIMD の対応状況（`go-fft` / `go-ndarray` が文書化している、マルチアーキテクチャの方針です）は次のとおりです。**amd64 SSE2**、**arm64 NEON**（axpy は VFMLA を使います。Go アセンブラにニーモニックのないベクトル倍精度の FMIN/FMAX は、生の命令語として出力しており、エンコーディングは実機で検証済みです）、**s390x z/vector**（VFMADB + VFMINDB/VFMAXDB。ビッグエンディアンですが、これらの要素ごとのカーネルはレーン順序に依存しません。オペランドの順序は qemu-s390x で検証しています）。**loong64 / ppc64le / riscv64** では、Go アセンブラに使えるベクトル倍精度演算がなく（riscv64 の場合は、既定の qemu CPU で V 拡張がフォールトします）、**スカラの内側ループにマルチコアのタイリング**を組み合わせています。それでもマルチコアによる高速化は得られます。SIMD カーネルはすべて、スカラのオラクルとビット単位で一致することを検証しています（axpy は、GOAMD64=v3 のビルドではオラクルが VFMADD に融合されるため、厳しい許容誤差での比較です）。演算全体は SciPy に対して検証しています。

## 結果 — 512×512（arm64 Linux、値が小さいほど高速） {#results-512512-arm64-linux-lower-is-better}

| 演算 | go-images **変更前** | go-images **変更後** | scikit-image / SciPy | SciPy との比較（変更後） |
|-------------------------|---------------------:|--------------------:|---------------------:|---------------:|
| **ボックスブラー**（r=5）      |            2,812,064 |             870,237 |           10,999,974 | **12.6× 高速** |
| **Sobel**（大きさ）   |              882,498 |             351,701 |            2,748,223 | **7.8× 高速** |
| **ガウスぼかし**（σ=3） |           12,900,987 |           4,259,656 |           16,029,709 | **3.8× 高速** |
| **Erode**（r=2）         |           13,865,054 |           1,581,921 |           10,559,638 | **6.7× 高速** |
| **Dilate**（r=2）        |           12,898,691 |           1,482,165 |           11,025,974 | **7.4× 高速** |

### フェーズ 1 のエッジ / フィルタの追加分 — 512×512（arm64 Linux、値が小さいほど高速） {#phase-1-edge-filter-additions-512512-arm64-linux-lower-is-better}

これらは新しいマルチコア（スカラの内側ループ）の演算で、同じ VM 上で、意味が一致する scikit-image / SciPy のリファレンスと比較して計測しています。まだ SIMD の内側ループはなく、高速化の要因はマルチコアへの分散と、より安価なアルゴリズム（メディアンでの計数による選択）です。それでも scikit-image をすでに上回っています。

| 演算 | go-images (ns/op) | scikit-image / SciPy (ns/op) | 高速化 |
|-------------------------|------------------:|-----------------------------:|---------:|
| **Scharr**（大きさ）  |         1,421,773 |                    3,833,147 | **2.7× 高速** |
| **Canny**（σ=1）         |        10,086,768 |                   27,031,572 | **2.7× 高速** |
| **Median**（r=2、5×5）   |        37,565,475 |                  214,597,360 | **5.7× 高速** |

意味の一致は次のとおりです。Scharr ⇔ 輝度プレーンに対する `skimage.filters.scharr`、Canny ⇔ `skimage.feature.canny(sigma=1, low=20, high=40)`、Median ⇔ チャンネルごとの `scipy.ndimage.median_filter(size=5, mode="nearest")`。Prewitt と SobelMag は Scharr のカーネルを共有します。UnsharpMask/Sharpen は GaussianBlur に、融合したピクセルごとの加算を組み合わせたものです（上記のガウスの数値が当てはまります）。メディアンの大きな差は、SciPy の汎用 n 次元メディアンに対する O(window+256) の計数による選択で生まれ、マルチコアのタイリングがそれをさらに広げています。次のベクトル化の対象は、エッジ系と Canny が共有する SIMD の Sobel 勾配カーネルの追加です。

「変更前」の列はスカラのシングルスレッドカーネル、「変更後」は SIMD + 4 コアです。**以前の 2 つの負けは、どちらも勝ちになりました。** ガウスは 0.92×（1.08 倍遅い）から **3.8× 高速**に、Erode/Dilate は約 0.9× から **6.7×/7.4× 高速**になりました。すでに勝っていたボックスブラーと Sobel は差を広げています（マルチコアのタイリングだけで、4 コアでおおよそ 3 倍になります）。

## 結果 — 1024×1024（arm64 Linux、値が小さいほど高速） {#results-10241024-arm64-linux-lower-is-better}

| 演算 | go-images (ns/op) | scikit-image / SciPy (ns/op) | 高速化 |
|-------------------------|------------------:|-----------------------------:|---------:|
| **ボックスブラー**（r=5）      |         7,548,773 |                   29,963,031 | **4.0× 高速** |
| **Sobel**（大きさ）   |         6,003,498 |                   11,327,476 | **1.9× 高速** |
| **ガウスぼかし**（σ=3） |        11,451,846 |                   46,418,949 | **4.1× 高速** |
| **Erode**（r=2）         |         7,896,837 |                   59,335,849 | **7.5× 高速** |
| **Dilate**（r=2）        |         7,893,893 |                   61,166,651 | **7.7× 高速** |

1024² では、scipy が大きな中間配列を実体化する演算（モルフォロジー、ガウス）で差が広がります。Sobel が 1.9× に縮まるのは、ピクセルあたりの演算量が小さく、高速化の大半がマルチコアへの分散によるものだからです（このサイズでは、SciPy のエッジフィルタは 1 回で済み、チャンネルごとの Python のオーバーヘッドもありません）。

### コンポーネントごとの高速化（512²、変更前 → 変更後） {#per-component-speed-up-512-before-after}

- **ガウス — スカラの下限より 3.0× 高速**（さらに SciPy も上回りました）。axpy SIMD カーネルが密な積和をベクトル化し、2 つのパスがコアに分散されます。垂直パスは、連続した行全体に対する純粋な axpy です。水平パスは内側の列をベクトル化し、境界でクランプされるわずかな列はスカラで処理します。
- **Erode/Dilate — スカラの下限より約 8.7× 高速:** ウィンドウごとの移動最小/最大が、プレーン上の連続した SIMD の MIN/MAX とマルチコアのタイリングになり、行ごとのスクラッチ領域は内側ループの外へ出しました（割り当ては 1 回あたり約 6,200 回から 71 回に減りました）。

> **更新 — O(1) の van Herk / Gil-Werman モルフォロジー。** モルフォロジーの内側ループは、その後、O(radius) の畳み込みから **O(1) の van Herk / Gil-Werman** の移動最小/最大に書き換えられました。1 ピクセルあたり 3 回の比較で、半径に依存しません。シングルスレッドの scikit-image 同等性ベンチマーク（Apple M4 Max）では、erode/dilate は 4096² で scikit-image の **同等 → 1.02×** に達し（従来は 0.58–0.77×）、全コアでは **4.8–7.8×** です。出力は `scipy.ndimage.grey_erosion`/`grey_dilation` とバイト単位で同一のままです。小さい半径での残りの差は、純粋な定数倍（SIMD）です。シングルスレッドとマルチスレッドの同等性の全表と方法論は、
> [BENCHMARKS.md](https://github.com/go-images/images/blob/main/BENCHMARKS.md) を参照してください。

> **更新 — 分岐なしの Sobel。** ピクセルごとに再計算していた Sobel の勾配（上で挙げた唯一の負けでした）は、その後解消しました。各行を、クランプでアドレス指定する境界の列と、行のベースをループの外へ出した**分岐なしの内側区間**に分けたため、内側では `clampIndex` の呼び出しが一切ありません。出力は素朴な実装とバイト単位で同一のままです。シングルスレッドの scikit-image 同等性ベンチマーク（Apple M4 Max）では、Sobel は scikit-image の **1.02–1.06×** に達し（従来は 0.78–0.80×）、全コアでは **4.2–4.8×** です。詳しくは
> [BENCHMARKS.md](https://github.com/go-images/images/blob/main/BENCHMARKS.md)
> のアクション項目 B を参照してください。

## SciPy に対する正しさ（速度だけではなく） {#correctness-vs-scipy-not-just-speed}

同じ VM で、決定論的な `64×48` の画像を使い、SIMD/マルチコアへの書き換え**後**の go-images の出力を、意味が一致する SciPy のリファレンスとピクセル単位で比較しました。

| 演算 | max \|Δ\| | mean \|Δ\| | 判定 |
|-----------|----------:|-----------:|---------|
| ボックスブラー  |         0 |      0.000 | **完全一致** |
| Erode     |         0 |      0.000 | **完全一致** |
| Dilate    |         0 |      0.000 | **完全一致** |
| ガウス  |         1 |      0.079 | 1 LSB 以内で一致（丸めのみ） |

SIMD/マルチコアへの書き換えで、数値上は**何も**変わっていません。ボックスブラーとグレースケールモルフォロジーは、これまでどおり SciPy とビット単位で一致します。ガウスも、最終クランプの最下位ビットの丸めだけが異なる点まで含めて、スカラ実装と同じ数値です。各 SIMD カーネルは、あらゆる長さの剰余についてスカラのオラクルとも照合しており（`internal/kernels/simd_test.go`）、分離可能な演算全体は、シリアルとパラレルの両方のしきい値で、独立した素朴なリファレンスと照合しています（`separable_test.go`）。

### 残る課題（正直に） {#residual-notes-honest}

- **メモリ:** プレーンベースのガウスは、従来のその場のバイト処理より多くの一時的な float64 スクラッチ領域を割り当てます（512² で ≈14.8 MB/op、従来は 2.1 MB）。これは連続した SIMD レイアウトの代償です。呼び出しごとに解放される一時的なもので、3.8× の高速化と引き換えになっています。再利用可能なスクラッチプールで減らすことは、今後の課題です。
- **loong64 / ppc64le / riscv64** はスカラの内側ループで動作し（Go アセンブラに使えるベクトル倍精度がない、qemu の V がフォールトする）、高速化はマルチコアのタイリングだけに頼っています。アーキテクチャごとの qemu CI ジョブで検証しています。

## 再現方法 {#reproducing}

```sh
# On the arm64 debian VM, with the repo synced to /tmp/goimages:
cd /tmp/goimages
GOWORK=off /usr/local/go/bin/go test -run=^$ \
  -bench 'BoxBlur|GaussianBlur|Sobel$|Erode|Dilate|Scharr|Canny|Median' -benchtime=2s ./...

# scikit-image / SciPy side (see the harness used to produce the table):
python3 skbench.py      # timings
python3 validate.py     # correctness vs scipy
```
